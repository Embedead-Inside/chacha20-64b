# chacha20-64b

[![License: MIT-0](https://img.shields.io/badge/License-MIT--0-blue.svg)](https://spdx.org/licenses/MIT-0.html) [![Language: C99](https://img.shields.io/badge/Language-C99-green.svg)](#)

ベアメタル・組込み向けの、**64バイト固定ブロック・インプレース**の ChaCha20 (RFC 8439) 実装です。
OS・`malloc`・外部ライブラリに依存せず、C99 の `stdint.h` のみで動作します。

> **注意**: 本実装は第三者による監査を受けていません。採用前に自身の責任で評価してください。

## 特徴

- **テーブル参照なし・秘密依存の分岐なし**（ARX構造）。S-box等のテーブルを持ちません。
- **インプレース処理**: 入力バッファを直接書き換えます。
- **アラインメント・エンディアン非依存**: バッファは任意のアドレスでよく（Cortex-M0 でも安全）、ビッグエンディアン環境でも RFC 8439 と同じ結果になります。
- **初期化と変換の分離**: 鍵・ナンス由来の状態は `init` で1回だけ作ります。
- **2つのビルド構成**（下記）。
- RFC 8439 のテストベクタと参照実装で検証済み（`make test`、CI: gcc/clang + UBSan/ASan）。

## 使い方

```c
#include "chacha20_64b.h"

void process_packet_256bytes(uint8_t packet[256], const uint8_t key[32], const uint8_t nonce[12]) {
    chacha20_64b_ctx_t ctx;
    chacha20_64b_init(&ctx, key, nonce);

    // 暗号化・復号は同一の呼び出し。カウンタをブロックごとに増やす
    chacha20_64b_transform(packet + 0,   &ctx, 0);
    chacha20_64b_transform(packet + 64,  &ctx, 1);
    chacha20_64b_transform(packet + 128, &ctx, 2);
    chacha20_64b_transform(packet + 192, &ctx, 3);

    chacha20_64b_wipe(&ctx); // 鍵素材を消去
}
```

RFC 8439 の AEAD (ChaCha20-Poly1305) と組み合わせる場合、データ暗号化のカウンタは **1 から**開始します（0 は Poly1305 鍵生成用）。

## API

| 関数 | 説明 |
|:--|:--|
| `chacha20_64b_init(ctx, key[32], nonce[12])` | ベース状態を生成 |
| `chacha20_64b_transform(buf[64], ctx, counter)` | 64バイトをその場で暗号化/復号 |
| `chacha20_64b_wipe(ctx)` | `ctx` を最適化で消されない形でゼロクリア |

## ビルド構成

| 構成 | 指定 | 特性 |
|:--|:--|:--|
| アンロール（既定） | なし | 10ダブルラウンドを展開。分岐なし、コードサイズ大 |
| コンパクト | `-DCHACHA20_64B_COMPACT` | ダブルラウンドをループ化。コードサイズ小 |

参考（x86-64 / gcc, `.text`）: `-Os` でアンロール約 4.2 KB、コンパクト約 1.1 KB。
ARM Cortex-M 等ではレジスタ数の制約があり、アンロールが速いとは限りません。**ターゲットで実測して選択してください。**

## セキュリティ上の注意

- **`(key, nonce)` を絶対に再利用しないでください。** 同じ組で別のデータを暗号化すると、2つの平文のXORが漏洩します。パケットごとにナンスを変えるか、単調増加カウンタ等で一意性を保証してください。
- **認証機能はありません。** ChaCha20 単体では改ざんを検知できず、暗号文のビット反転が平文に反映されます。Poly1305 等のMACと組み合わせてください。
- **カウンタは32ビットで折り返します。** 同一 `(key, nonce)` で 2^32 ブロック（256 GiB）を超えて使用しないでください。
- **`wipe` の範囲**: `ctx` 内の鍵素材のみを消去します。`transform` 実行中にレジスタ/スタックへ残る一時値は対象外です。
- 「サイドチャネルに強い」とは保証しません。テーブル参照と秘密依存分岐がない設計というだけで、コンパイラ・CPU依存の影響は別途確認してください。

## テスト

```sh
make test
```

RFC 8439 §2.3.2（ブロック関数）、§2.4.2（暗号化）、参照実装（Python `cryptography`）との照合、非アラインバッファ、往復（暗号化→復号）を、アンロール版・コンパクト版の両方で検証します。
